**Why did you retrieve both `categoryDetails` and `projects` in the controller before calling `res.render()` instead of having the EJS view retrieve that data itself?**

User:
This comes down to what each layer of MVC is responsible for.

**Views should only display data, never fetch it.** EJS templates aren't meant to talk to the database — they don't import model functions or run queries. Keeping data-fetching out of the view keeps `category.ejs` focused purely on presentation: looping through what it's given and rendering HTML.

**`res.render()`** **needs the data up front, not after.** Once EJS starts rendering the template, it's just filling in HTML with whatever values it's handed, there's no way for the view to "go fetch more data mid-render" and have that work cleanly with an `async` database call. The data has to already be resolved *before* `render()` is called.

**It matches the MVC separation of concerns you've followed throughout the app.** The Model owns the database code, the Controller pulls together whatever the page needs and hands it off, and the View just displays it, same pattern as every other page (`organization.ejs`, `project.ejs`, etc.).

So the controller `await`s both pieces first, packages them into one object, and only then calls `res.render('category', { title, categoryDetails, projects })`, by that point, the view has everything it needs and doesn't have to do anything but display it.

// Catch-all route for 404 errors
app.use((req, res, next) => {
    const err = new Error('Page Not Found');
    err.status = 404;
    next(err);
});

// Global error handler
app.use((err, req, res, next) => {
    // Log error details for debugging
    console.error('Error occurred:', err.message);
    console.error('Stack trace:', err.stack);

    // Determine status and template
    const status = err.status || 500;
    const template = status === 404 ? '404' : '500';

    // Prepare data for the template
    const context = {
        title: status === 404 ? 'Page Not Found' : 'Server Error',
        error: err.message,
        stack: err.stack
    };

    // Render the appropriate error template
    res.status(status).render(`errors/${template}`, context);
});

// Test route for 500 errors
const testErrorPage = (req, res, next) => {
    const err = new Error('This is a test error');
    err.status = 500;
    next(err);
};

Assistant:
Good, Kingsley. You’ve now provided all four required code areas, and your error-handling strategy is clear: the catch-all middleware creates a 404 error, while the global handler determines whether to render the 404 or 500 page.

I want to focus on one important detail in your design.

**Why do you call `next(err)` in both the 404 middleware and `testErrorPage` instead of calling `res.render()` directly from those functions?**

User:
Calling `next(err)` hands the error off to Express's **global error handler** (the four-parameter `(err, req, res, next)` middleware) — which is the *single place* in your app that decides what to render, based on the error's status. That handler is what actually calls `res.render()`.

If the 404 middleware and `testErrorPage` called `res.render()` directly instead, you'd be duplicating that rendering logic (choosing the template, building the context object, logging) in every place an error can occur. Worse, they'd bypass your centralized error handler entirely, so any future change to *how* errors are displayed (a new field in the context, different logging, a different template name) would have to be updated in multiple places instead of one.

`next(err)` also works with Express's built-in error-detection: passing an argument to `next()` tells Express "this isn't a normal continue, this is an error", which is what makes it skip past any remaining normal middleware and go straight to the error handler. Calling `res.render()` directly wouldn't trigger that routing behavior at all.
