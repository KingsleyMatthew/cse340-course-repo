-- ========================================
-- Category Table
-- ========================================
CREATE TABLE category (
    category_id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL UNIQUE
);

-- ========================================
-- Project-Category Join Table
-- ========================================
-- A project can belong to one or more categories, and a category can be
-- associated with one or more projects, so this many-to-many relationship
-- requires its own table. The composite primary key prevents the same
-- project/category pair from being inserted more than once.
CREATE TABLE project_category (
    project_id INTEGER NOT NULL REFERENCES service_projects(project_id),
    category_id INTEGER NOT NULL REFERENCES category(category_id),
    PRIMARY KEY (project_id, category_id)
);

SELECT category_id, name
FROM public.category;

Coach: Nice, Kingsley. You’ve shared a solid example of a many-to-many relationship: a project can have multiple categories, and a category can belong to multiple projects. The PRIMARY KEY (project_id, category_id) also prevents duplicate combinations.
Why did you need the project_category join table instead of putting a single category_id column directly inside the service_projects table?

Kingsley: A category_id column on service_projects only allows one category per project (a one-to-many relationship). But the requirement was a many-to-many relationship — a project can have multiple categories, and a category can span multiple projects. A single column can't represent that; a join table can, since it lets a project appear in multiple rows, once per category it belongs to.

Coach: Excellent, Kingsley. That explanation shows you understand the reason behind the database structure, not just what the SQL says.
What does this query do, and why would you use SELECT category_id, name FROM public.category instead of simply selecting * from the table?

Kingsley: It selects only the category_id and name columns from every row in category — not everything.
Naming the columns explicitly (instead of SELECT *) means the query only returns what the code actually uses, and won't unexpectedly change if I adds a new column to the table later. It also matches the pattern used in your other models.

Coach: That’s a strong explanation, Kingsley. You understand both what the query returns and why explicitly naming the columns is a better practice here.

import db from './db.js'

const getAllCategories = async() => {

        SELECT category_id, name
      FROM public.category;
    `;

    return result.rows;
}

export {getAllCategories}

Coach: Good, Kingsley. This function shows the full basic flow: it imports the database connection, defines an asynchronous function, builds the SQL query, sends it to PostgreSQL with db.query(), and returns the rows.

Kingsley: async is needed because await only works inside an async function. At await db.query(query), the function pauses and waits for Postgres to respond — without blocking the rest of the app — then resumes with the result once the database replies.

Coach: Exactly, Kingsley. You’ve got the important distinction: await lets this particular function wait for the database operation to finish without freezing the whole Node.js application.
