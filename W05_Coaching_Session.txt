const findUserByEmail = async (email) => {
    const query = `
        SELECT u.user_id, u.name, u.email, u.password_hash, r.role_name
      FROM public.users u
      JOIN public.roles r ON u.role_id = r.role_id
      WHERE u.email = $1;
    `;

    const queryParams = [email];
    const result = await db.query(query, queryParams);

    if (result.rows.length === 0) {
        return null; // User not found
    }

    return result.rows[0];

const verifyPassword = async (password, passwordHash) => {
    return bcrypt.compare(password, passwordHash);
}

const authenticateUser = async (email, password) => {
    const user = await findUserByEmail(email);

    if (!user) {
        return null;
    }

    const passwordIsValid = await verifyPassword(password, user.password_hash);

    if (!passwordIsValid) {
        return null;
    }

    // Don't carry the password hash around outside the model
    delete user.password_hash;

    return user;
}



const processLoginForm = async (req, res) => {
    const { email, password } = req.body;

    const user = await authenticateUser(email, password);

    if (user) {
        // Store the authenticated user on the session
        req.session.user = user;

        req.flash('success', 'Login successful!');
        console.log('User logged in:', user);

        return res.redirect('/dashboard');
    }

    req.flash('error', 'Invalid email or password. Please try again.');
    res.redirect('/login');
};

Assistant: Good. Your login flow has a clear separation of responsibilities:

- `findUserByEmail()` retrieves the user and their stored bcrypt hash.
- `verifyPassword()` uses `bcrypt.compare()` rather than trying to decrypt the hash.
- `authenticateUser()` confirms both the account and password, then removes `password_hash`.
- `processLoginForm()` stores the authenticated user's information in `req.session.user`, which allows later requests to recognize the logged-in user.

One thing I especially want you to understand is that the session does not store the user's password; it stores the authenticated user's information after successful verification.

Why is `req.session.user = user` useful after the password has been successfully verified?

User: Without it, the server would forget who's logged in the moment the response finishes — HTTP requests are stateless by default, so every new page request would otherwise require logging in again from scratch. Storing the user on `req.session.user` lets the server recognize the same logged-in user across every subsequent request (viewing the dashboard, checking `isLoggedIn` in the nav, enforcing `requireLogin`/`requireRole`), without needing to re-verify the password each time.

Assistant: Exactly. You’ve captured the purpose of sessions well: HTTP is stateless, while the session gives your application a way to maintain authenticated state between requests.

### Topic 3: Protected Access Middleware

Now we’ll look at how your application prevents unauthenticated users or users without the required role from accessing protected routes.

Please paste the code for your `requireLogin` and `requireRole` middleware.

User:
const requireLogin = (req, res, next) => {
    if (!req.session || !req.session.user) {
        req.flash('error', 'You must be logged in to access that page.');
        return res.redirect('/login');
    }
    next();
};

const requireRole = (role, redirectTo = '/') => {
    return (req, res, next) => {
        if (req.session && req.session.user && req.session.user.role_name === role) {
            return next();
        }

        req.flash('error', 'You do not have permission to access that page.');
        res.redirect(redirectTo);
    };
};

Assistant: Good. This middleware gives you two different layers of protection:

- `requireLogin` checks whether a session contains an authenticated user. If not, it redirects them to `/login`.
- `requireRole` goes one step further and checks the authenticated user's `role_name` before allowing access.
- Calling `next()` is what allows the request to continue to the protected route when the check succeeds.
- The `return` before the redirect in `requireLogin` also prevents execution from continuing after the response has been sent.

Why do you need both `requireLogin` and `requireRole` instead of using only `requireLogin` for every protected route?

User: Because they check different things. `requireLogin` only confirms *someone* is logged in — it says nothing about *who*. A regular logged-in user would pass `requireLogin` just fine, but they still shouldn't be able to create organizations, edit projects, or view the admin users list. `requireRole('admin')` adds a second, stricter check: not just "are you logged in," but "do you specifically have the admin role." Using only `requireLogin` everywhere would let any registered user access admin-only features — you need `requireRole` wherever access should depend on *which* role the user has, not just whether they're authenticated at all.

Assistant: Exactly. You’ve clearly distinguished authentication from authorization:

- `requireLogin` → Are you authenticated?
- `requireRole('admin')` → Are you authorized for this particular action?

That distinction is important because being logged in does not automatically mean a user should have access to every part of the application.

That completes Topic 3: Protected Access Middleware.
